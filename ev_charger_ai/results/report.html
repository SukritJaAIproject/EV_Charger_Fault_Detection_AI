3. ความไว vs ความแม่น — trade-off ที่ต้องเลือก

Recall (จับปัญหาได้) เทียบ False Alarm Rate (เตือนผิดใน session ปกติ)

เป้าหมายคือมุมขวาล่าง: จับได้มาก + เตือนผิดน้อย

5. บทเรียนจากสนามจริง

  • ตู้ชาร์จ 2 หัวแชร์กำลังกัน — กระแสตกจาก 129 A เหลือ 54 A กลางคันเป็นเรื่อง "ปกติ" เมื่อรถอีกคันเสียบชาร์จ กฎแบบสเปค (current collapse) จึงเตือนผิดถล่มจนต้องออกแบบใหม่ — โมเดลที่เรียนรู้จากข้อมูล (XGBoost/AE) แยกแยะเองได้
  • 79% ของปัญหาคือการชาร์จขาดกลางคัน (ไม่มี SessionStop) ซึ่งส่วนใหญ่ตายทันทีไม่มีอาการนำ — เพดานของ "การเตือนล่วงหน้า" จึงถูกกำหนดโดยธรรมชาติของปัญหา ไม่ใช่ตัวโมเดล
  • สัญญาณนำที่ใช้ได้จริง: SLAC retry (นำหน้าการเชื่อมต่อล้มเหลว), retransmission storm และ dialog gap ที่ยาวผิดจังหวะ (นำหน้า abort), isolation Warning แบบต่อเนื่อง
  • ความรู้เฉพาะ fleet ที่ฝังไว้ในโมเดลแล้ว: EVSENotification ใช้ค่า StopCharging, PLC บางสถานี retransmit สูงถึง 40 ครั้ง/นาทีแบบปกติ, dialog gap 2–3 วิ เกิดเป็นระยะใน session ดีๆ

7. พร้อม deploy จริง

  • ทุกโมเดลคือ Python class ที่ implement Detector.observe(event, features) — ต่อกับ live capture ได้ทันที (tshark → parser เดียวกับ pipeline)
  • Inference เป็น numpy ล้วน (ตรวจสอบแล้วผลตรงกับ torch/sklearn ทุกตำแหน่ง) — server ปลายทางไม่ต้องมี GPU ไม่ต้องลง torch ก็รันได้ ใช้เวลา 22–585 µs/event เทียบกับ event rate จริง ~12 events/วินาที/หัว = เหลือเฟือหลักพันเท่า
  • โค้ด + โมเดลทั้งหมดอยู่ที่ F:\pcap_downloads\ev_charger_ai (README มีขั้นตอน reproduce ครบ) · GPU env: conda ev_ai (torch 2.11 + CUDA 12.8)
  • คำแนะนำ: deploy แบบ 2 ชั้น — Traditional AI เป็นด่านหลัก (แม่น เข้าใจง่าย อธิบายได้) เสริมด้วย Agentic AI สำหรับสถานีที่มีปัญหา SLAC/PLC เรื้อรัง แล้วเก็บ label จากช่างภาคสนาม มา retrain XGBoost/RL ให้แม่นขึ้นเรื่อยๆ
ข้อจำกัดที่ควรรู้: ground truth มาจาก semantics ของโปรโตคอล (ไม่มี label จากช่างภาคสนาม) — SESSION_ABORT บางส่วนอาจเป็นผู้ใช้ดึงปลั๊กเอง ซึ่งแยกจากปัญหาอุปกรณ์ไม่ได้จากข้อมูลฝั่งสื่อสารเพียงอย่างเดียว และ threshold ของ agent-based ปรับจากสถานี train เท่านั้น (ไม่เห็น test)
